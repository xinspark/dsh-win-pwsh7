# 02 · 用限制后的 visible 规划隐藏 → hide/restore 振荡卡死宿主

- 类别: 并发 / 生命周期
- 日期: 2026-11-03
- 状态: 已修复（0.2.2）

## 症状

0.2.1 的 dsh-ops 共存桥在多个 agent 的会话恢复后，宿主主线程被占满：工具面在
“隐藏官方 read/glob/grep/bash”和“恢复它们”之间反复切换，`tools/change` 被不断触发，
Host 看起来像卡死。

## 根因

桥用 `tools.view(agent).visible` 规划 deny 列表，而 `visible` 是 **restrict 之后**的视图。
第一次隐藏成功后，下一次 reconcile 看到对应 OPS 工具不再成对，就认为“不需要隐藏”并撤回
restriction；撤回后官方工具又出现，再次隐藏——每个来回都 emit `tools/change`，又同步触发
下一次 reconcile，形成隐藏/恢复振荡。agent 越多，循环越重。

## 证据

- `CHANGELOG.md` 0.2.2 节：改为读限制前的 `knownNames` / `restrictableNames`，并只保留
  `tools.restrict()` 接受的名字；
- `tools/check-host.mjs` 的 `the bridge plans from pre-restriction names, so hiding cannot flip it`
  用同一份 `knownNames` 连续规划两次，断言 deny 列表不变；
- `the fallback view latches the names already hidden instead of oscillating` 覆盖老宿主只有
  `visible` 时的退路：把已隐藏的名字并入事实集合；
- `a scope-local name cannot make the whole restriction plan throw` 覆盖 scope-local 的
  `ops_bash`：它不能进入全局 deny 列表。

## 结论

1. 规划要基于**限制前**的事实；限制后的视图只能用来展示；
2. 任何“写入会触发自身监听器”的 reconcile，都要有 `mutating` 重入保护与稳定事实源；
3. 桥的 deny 列表必须过滤到 `restrictableNames`，一个不可接受的名字会让整次 restrict 抛错。
