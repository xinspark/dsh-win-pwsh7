# 07 · 同一个可执行文件被三条读取路径各探一次

- 类别: 性能 / 门的盲区
- 日期: 2026-11-15
- 状态: 已修复（0.2.11）

## 症状

没人报过。这不是用户可见的缺陷，是一次状态调用里**多起了两个进程**：

```
pwsh7_status 一次调用 → pwsh -EncodedCommand 启动 3 次（同一个 exe）
tools/pre-execute 一次 gate 刷新 → 同样 3 次
```

报告文字完全正确，gate 判定也完全正确 —— 所以它不会以任何"错误"的形式出现，只会让每次
`pwsh` 调用和每次打开插件页多等两个进程启动的时间。9 个月里没人发现。

## 根因

判定要从**三个不同来源**读同一件事，三者常常指向同一个文件：

| 读取点 | 来源 | 缘何存在 |
| --- | --- | --- |
| `detect()` | `overridePath` + 独立 resolver | 探测与推荐 |
| `executorRows()` | 执行器行声明的 `pwshPath` | 报告与降级读法 |
| `shellRuntimeReading()` | `ctx.shell.pwshPath` getter | 权威的"会运行什么" |

每个读取点都各自 `probeVersion()`，没有任何一层共享结果。三条路径是**分别合理**的（每一次
都读到一个不同的真相来源），合起来就成了三倍成本 —— 这是"多个正确读法"的合成缺陷。

## 证据

- 0.2.11 前，`tools/check-host.mjs` 的两条探针计数断言各报
  `one status call spawned 3 probes of C:\Windows\System32\cmd.exe`（先红后绿，红值是实测值）；
- 修复后各报 1；
- 实现：`createProbeCache()` 在一个读取周期内记住**探针的 promise**（不是值 —— 两个并发读者
  共享同一个进程）；周期由 `pwsh7_status` 的 execute / `renderStatus` / `refreshGate` /
  `activationSweep` 各建一次；
- **刻意不做 TTL**：跨周期复用会把"刚装好之前的运行时"喂回 gate，那正是 60 秒刷新要关的口子；
  安装轮询 `awaitRuntime` 仍然每轮新周期。

## 结论

1. **"多个正确读法"会合成一个成本缺陷**：当同一条事实有 N 个真相来源时，先问"它们多久指向
   同一个东西"，再问"我是不是在对它做 N 次 I/O"；
2. **去重的边界应该是"答案不会变"的窗口**，不是时间。读取周期是这个项目里唯一安全的窗口：
   周期内"会运行什么"不可能在报告脚下改变，所以共享不会 stale；换成 TTL 就立刻有了
   [经验 05](05-执行器缓存.md) 那个坑的反面版本；
3. **这类缺陷必须由计数断言抓**，不能靠读代码：三处 `await probeVersion(ctx, path)` 分散在
   700 行里，每一处单独看都对，只有"数进程"能看出合计；
4. 加新的读取路径时，先看它有没有拿到周期缓存 —— 没有拿到，它就又开了一个进程。
